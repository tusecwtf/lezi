# 记录首页：计划与时间轴左滑编辑 / 右滑删除

| 字段 | 值 |
|------|-----|
| **Date** | 2026-07-29 |
| **Status** | Spec |
| **Related** | `docs/prd/ui.md` §5.2、§5.4、§7；`docs/adr/0001-separate-care-plans-from-care-records.md`；Composer 删除确认 |

## Overview

在记录 Tab 首页的**护理计划行**与**时间轴记录行**上，增加与常见 IM/邮箱一致的横向滑动次要动作：

- **左滑** → 编辑（绿色满铺反馈）
- **右滑** → 删除（红色满铺反馈；**始终**二次确认）

方向为**屏幕绝对方向**，不随 `preferredHand` 镜像。左手布局只作为优先验证场景；惯用手契约仍只约束底部快捷坞。

## Goals

1. 统一计划与记录的左右手势语法，降低「改 / 删」发现成本。
2. 计划点按主路径保持**履行**；滑动不抢走夜喂一次点按完成。
3. 删除不绕过现有确认强度；列表可快达确认，但确认前不软删除。
4. `warm` / `journal` 共用同一手势与 domain，不复制两套业务。

## Non-goals

- 搜索结果列表、乐记日历计划行（后续可复用同一 cell 手势组件）。
- 右滑免确认、Snackbar Undo 作为主安全网。
- 随惯用手镜像滑动方向。
- 把「跳过计划」塞进滑动。
- TalkBack 自定义动作（首版明确不做；见 §无障碍）。
- 改变家庭 ACL（谁可管计划/记录仍跟现 domain）。

## Surface

| 包含 | 不包含 |
|------|--------|
| 记录 Tab：待履行/已错过**计划区** + **时间轴记录** | 搜索页 |
| 换日到非今日（同一套 cell） | 乐记日历、Widget |
| `warm` 与 `journal` | 布局编辑态、快捷坞 |

## Interaction matrix

| 行类型 | 点按（关闭态） | 左滑（绿） | 右滑（红） | 行上其它可见控件 |
|--------|----------------|------------|------------|------------------|
| 护理计划 | **履行**（`Fulfill`） | **编辑计划**（`EditPlan`） | **删除确认** | 可管理时保留 **「跳过」**；**去掉**可见「编辑」 |
| 护理记录 | **编辑**（`Edit`） | **编辑**（与点按同效） | **删除确认** | 无额外按钮 |

### 仅本机 / 同步琥珀态

- **点按**：仍优先打开既有同步说明（publish chrome），不进编辑。
- **左滑编辑**：仍**直达编辑**（意图是改内容，不被同步态劫持）。
- **右滑删除**：有权限则仍走列表删除确认（与编辑页删除同一 domain）。

### 权限

| 情况 | 行为 |
|------|------|
| 该方向无权限 | 不跟手，或跟手松手回弹 + 轻提示；**不**呈现可完成的假红/绿成功态 |
| 仅一侧有权 | 只启用有权方向 |
| 计划履行 | 任意成员点按履行**不受**管理权限影响 |
| ACL 来源 | 计划：现有 `manageablePlanIds` / ADR-0001；记录：与 Composer 删除/编辑同一规则 |

## Gesture model（混合双档）

绝对方向（内容相对屏幕；**卡片不位移**，色块在卡内生长）：

- 手指**左**滑 → 卡片**右侧**起绿色逐渐填充 → **编辑**
- 手指**右**滑 → 卡片**左侧**起红色逐渐填充 → **删除确认**

（与用户口述「左滑编辑、右滑删除」一致；视觉为卡内填充而非整卡平移露底。）

| 参数 | 值 | 说明 |
|------|-----|------|
| 半程 reveal 吸附 | 行宽 **≈28%** | 松手停在可点色区；工程可 ±5% |
| 满行程触发 | 行宽 **≈55%** | 松手直接触发该侧动作 |
| 回弹/吸附动画 | **~200ms** | |
| Haptic | 越过**满行程阈值**时轻度一次 | 跟手过程不连续震动 |

### 完成态

1. **半程**：吸附展开；点绿色区 → 编辑；点红色区 → 删除确认。
2. **满行程松手**：左 → 打开编辑；右 → 打开删除确认（仍须确认框，不直接删）。
3. **同时最多一行** reveal；以下情况收起已展开行：
   - 开始滑另一行
   - **纵向列表滚动**
   - 打开编辑面板或删除确认框
4. **展开时点正文**（非绿/红区）→ **只收起**，不触发履行/编辑。
5. 关闭态点正文 → 矩阵中的点按语义不变。

## Visual

- 卡片**固定不平移**；滑动进度 = 卡内色块宽度占比（满高、外缘贴合卡片圆角）。
- **编辑**：自右向左生长 `Success` 绿填充 + 铅笔图标 +「编辑」（色条够宽后显示文案）。
- **删除**：自左向右生长 `error` / `Danger` 红填充 + 垃圾桶图标 +「删除」。
- 未着色区域仍可点按（展开时点正文只收起；关闭态点按语义不变）。
- 深色模式使用同一语义 token，保证文字/图标对比。
- **禁止**用计划「已错过」琥珀、宝宝主题色冒充绿/红，避免与状态色、危险语义混淆。
- PRD 已约束：计划状态色不用同时承担保存失败或医疗危险的红色；本滑动删除红仅出现在**手势动作层**，不是计划状态色。

## Delete path

1. 右滑触发 → **列表级** `AlertDialog`（不先打开 Composer）。
2. 文案与 Composer 内删除一致：
   - 计划：`carePlanDeleteConfirmation`（含提醒、系统日历、不生成记录、无法撤销）。
   - 记录：标题「删除这条记录？」；影响「删除后会从时间轴和汇总中移除，无法撤销。」
3. 确认 → 调现有 domain 软删除 / 计划删除；成功 toast：`已删除护理计划` / `已删除记录`。
4. 取消或 dismiss → 行回弹收起；无写入。
5. 删除失败 → 确认框内展示错误（与 Composer 删除失败体验对齐），框不自动关。

## Edit path

| 行 | 左滑 / 点绿 | Composer 请求 |
|----|-------------|---------------|
| 计划 | 编辑安排 | `RecordComposerRequest.EditPlan(id)` |
| 记录 | 编辑事实 | `RecordComposerRequest.Edit(id)` |

记录左滑与点按同目标时，实现应复用同一入口，避免两套预填逻辑。

## 无障碍（首版取舍）

**明确接受：**

- 不做行级 TalkBack 自定义动作「编辑」「删除」。
- 记录：读屏用户点按进编辑，再在面板内删除（既有路径）。
- 计划：去掉可见「编辑」后，**TalkBack 首版无法编辑计划**；可读路径为履行（点按）与「跳过」。
- 计划编辑仅视力用户左滑可达。

后续若回收该缺口，优先恢复计划行可见「编辑」或补自定义动作，而不改左右滑语义。

## 单手布局

- `preferredHand=left|right` **不**改变滑动方向或绿/红位置。
- 验收须在**左手**与右手下各走通：计划履行/编辑/删除、记录编辑/删除；确认坞镜像与列表手势互不干扰。

## Implementation notes（非绑定，供实现）

- 在 `designsystem` 或 `feature/log` 抽可复用 `SwipeEditDeleteRow`（或等价），包裹现有 `RecordRow`。
- 横向拖动手势与纵向 `LazyColumn` 竞争时：明显横滑锁横轴，纵滑交给列表；与下拉同步手势共存时以系统嵌套滚动惯例为准。
- 打开确认框前清除 reveal 偏移，避免对话框下仍露红底。
- 单元测试可抽纯函数：偏移比 → `SettledClosed | RevealedEdit | RevealedDelete | CommitEdit | CommitDelete`。
- UI 测试 tag 建议：`timeline_swipe_edit_*` / `timeline_swipe_delete_*`；计划保留 `care_plan_skip_*`，移除对 `care_plan_edit_*` 可见按钮的依赖（改为滑动或 Composer 深链测试）。

## Acceptance

1. 计划：点按 → 履行；左滑/点绿 → 编辑计划；右滑/点红 → 确认后删除；「跳过」仍在；无可见「编辑」按钮。
2. 记录：点按 → 编辑；左滑 → 编辑；右滑 → 确认后删除。
3. 双手方向一致；左手偏好下行为与右手相同。
4. 换日列表同样可滑。
5. 无权限方向无法完成动作；有提示或回弹。
6. 琥珀记录：点按同步说明，左滑仍进编辑。
7. 多行不并开；滚动收起；展开点正文只收起。
8. 删除确认文案与 Composer 一致；取消不删。
9. `warm` / `journal` 均可用。
10. 阈值与 haptic 符合 §Gesture model（允许工程 ±5%）。
