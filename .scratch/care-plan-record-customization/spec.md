# Spec: 护理计划、记录自定义与照片原子同步

Status: implementation-complete; final Release revalidation pending
Feature: care-plan-record-customization  
Product: 乐记 (`com.lezi.babylog`)  
Source: conversation grill 2026-07-26 · `/to-spec`

## Problem Statement

乐记当前把记录入口、未来安排、日历事项、照片与项目设置分散在多条路径中：记录只允许过去或当前时间；日历仍以自由标题事项为主；首页快捷栏固定；“记录设置 / 自定义项目 / 记录项目”彼此割裂；照片只在部分文本类型中出现且上限不统一；不可保存时的确认按钮既缺少稳定视觉，也不能直接解释具体问题。

如果直接允许把未来时间写进护理记录，尚未发生的意图会污染时间轴、汇总、搜索与导出。如果照片与记录或计划分批同步，家庭成员又会看到缺图事实、缺图计划，甚至提前安排内容尚未完整到达的提醒。系统日历还带来权限、隐私披露、目标日历选择与重复提醒问题，不能被当作普通本地字段处理。

本需求需要把这些变化收敛为一条一致的领域路径：已经发生的是护理记录，未来的是护理计划；计划到点只提醒，履行后才产生事实记录；记录与计划的照片都作为完整同步包的一部分；所有新建入口都指向具体记录项目；快捷槽位、项目启用和顺序在统一设置中管理；系统日历只是当前设备可选的单向副本。

## Solution

1. 引入与护理记录分离的单次 `CarePlan`。统一 Record Composer 提供“记录事实”“安排护理”“完成护理计划”三种明确模式，未来时间只能保存为计划。
2. 在记录明细最上方展示待履行计划：当天先列已错过，再列当天待执行；查看其他日期时只列所选日期。提醒、乐记日历和该区域都可进入履行面板。
3. 护理计划在家庭内共享。任意成员均可创建和履行；普通成员只能修改、跳过或删除自己创建的计划，管理员可管理全部。同步冲突按角色、履行确认时间和 UUID 稳定裁决为唯一事实。
4. 所有已启用的具体记录项目都可安排为计划。取消新建“备注 / 其他 / 泛化自定义”入口，保留历史记录兼容；具体自定义项目直接成为可选择项目。
5. 首页保留四个可配置常用槽位，并固定一个“更多”入口。类别和类别内项目均可拖动排序；项目不得跨类别移动；布局偏好只保存在当前设备。
6. 把记录相关配置合并为“记录与快捷设置”，包含常用记录、所有记录项目、分项目设置、护理计划与日历。
7. 任意记录类型和护理计划的公共备注区均支持最多三张照片，可插入、预览、滑动、删除。履行计划时默认带入计划照片，并允许确认前调整。
8. 记录加全部照片、计划加全部照片分别作为原子家庭同步包。接收方只有在实体与全部照片就绪后才能看见；失败时创建者本机保留完整内容并显示仅本机状态。
9. 用户可主动授权把计划单向投影到自己选择的 Android 可写日历。每条计划开关默认开启；首次配置默认选择第二级披露“宝宝昵称 · 记录类型”，但必须由用户确认。
10. 不可保存时，确认按钮保持正常形状和尺寸并呈灰态。用户仍可点击它查看具体原因卡和定位首个问题，但不会保存；保存中和删除中则真正不可点击。

## Implementation Decisions

### 领域边界与状态

- 护理记录是已发生事实；护理计划是未来意图。两者使用不同实体、查询与同步语义，不以“带未来时间的 Record”兼容。
- `CarePlan` 至少表达：稳定 UUID、家庭与宝宝、具体记录项目身份、计划字段快照、文字备注、计划时刻、创建时区、创建者 membership、状态、系统生成时间、更新版本、软删除、履行关联，以及本机可解释的同步发布状态。
- 状态只有 `pending`、`missed`、`completed`、`skipped`。`missed` 可由当前绝对时刻超过计划时刻且仍未完成/跳过派生，不要求后台任务改写。
- 到点提醒不是履行。只有“完成并记录”成功写入实际护理记录，计划才进入 `completed`。
- 履行结果保存不可编辑的履行确认时间；实际发生时间仍可调整，但不参与冲突裁决。
- 已完成计划与权威护理记录保持稳定关联。跳过保留计划审计语义；删除使用 tombstone 并从常规计划视图移除。

### 时间与转换规则

- 新建草稿主时间在未来时，Composer 明确采用“安排护理”并创建 CarePlan；当前或过去时间创建 Record。
- 编辑既有 Record 并把主时间改到未来，保存前确认“转为护理计划”。确认后在一个本地事务中软删除原记录、创建计划、转移字段/备注/照片并生成同步变更；取消则不保存。
- 编辑 CarePlan 时把计划时刻改到当前或过去，仍保存为计划并呈 `missed`，绝不自动写 Record。
- 计划时刻存绝对 instant 与创建时区 ID。设备时区不同时显示本地换算结果并补充原计划时间。
- 履行 Composer 允许把实际发生时间调整为当前或过去，但不能确认未来的实际护理记录。

### Composer 与入口

- 深化现有 Record Composer，不新建平行计划编辑器。公开请求语义扩展为：新建事实、编辑事实、新建计划、编辑计划、履行计划。
- 三种可见模式为“记录事实”“安排护理”“完成护理计划”；复用字段、公共备注与照片区，但标题、主按钮、时间语义和可用操作明确变化。
- 快捷槽位、“更多”、乐记日历“＋”、提醒、记录明细待履行卡和历史日程显式转换均进入统一 Composer。
- 状态型项目在安排时只保存意图；母乳不启动计时，睡眠不创建开放区间。履行时才进入相应状态动作或手动补记。
- 计划照片在履行草稿中默认成为记录照片，确认前可删除、替换和补充，但总数仍不超过三张。

### 待履行视图

- 计划区固定在实际记录列表最上方，不把计划伪装成普通记录行。
- 今天先显示全部已错过未处理计划，再显示今天尚未到点计划；组内均按计划绝对时刻升序。
- 非今天只查询所选本地日期对应的计划。待执行用主题强调色，已错过用琥珀色。
- 提醒、乐记日历计划和待履行卡都携带稳定计划身份进入同一履行请求。

### 家庭权限与冲突

| 动作 | 普通成员 | 管理员 |
|------|----------|--------|
| 创建计划 | 允许 | 允许 |
| 履行任意计划 | 允许 | 允许 |
| 修改、跳过、删除自己创建的计划 | 允许 | 允许 |
| 修改、跳过、删除他人创建的计划 | 不允许 | 允许 |
| 查看冲突审计并转独立记录 | 不允许 | 允许 |

- 创建者离开家庭后，管理员成为可管理方；计划不自动删除。
- 同一计划的履行候选只选择一个权威事实，比较键依次为：提交者是否管理员、不可编辑的履行确认时间（更早优先）、候选 UUID（稳定排序）。
- NAS 到达时间、可编辑的实际发生时间和本机更新时间不得用于裁决。
- 落选候选标记 `conflict-not-adopted`，保留内容、提交者、确认时间与计划关联；不进入正常 Record 查询、汇总、搜索或普通导出。
- 管理员“转为独立记录”时创建新的 Record 身份并保留来源审计关联，不能把落选项直接翻成第二权威履行。

### 项目、自定义定义与历史兼容

- 新建目录只包含已开启的具体内建项目与具体自定义项目。`memo`、`other`、泛化 `custom` 不再作为新建项目、计划类型或快捷候选。
- 历史 `memo`、`other`、`custom` Record 保持可读和可编辑，不做破坏性迁移。
- 历史自由标题 CalendarEvent 保持本机可见、可编辑和提醒，不进入家庭同步；显式转换才创建 CarePlan。
- 自定义项目共享稳定 UUID、名称、图标、创建者和 tombstone；历史 Record/CarePlan 保存名称与图标快照，改名或删除不改写历史。
- 任意成员可创建和使用自定义项目。普通成员仅管理自己创建的定义；管理员管理全部并接管离开成员的定义。
- 自定义项目的本机启用、展示类别顺序、类别内顺序与快捷槽位不是家庭共享字段。

### 四槽快捷栏与统一设置

- 首页固定四个可配置槽位加一个“更多”。四槽整体靠偏好手一侧，“更多”位于远侧。
- 槽位存稳定项目身份，可为空；名称或图标更新后跟随定义。睡眠等状态型项目继续根据领域状态生成动作外观和文案。
- 项目关闭、删除或旧泛化入口移除时，槽位变为“＋ 选择常用记录”，不自动替换。迁移默认依次映射尿尿、睡眠、母乳、配方奶。
- 顶层只保留“记录与快捷设置”，二级固定为：常用记录、所有记录项目、分项目设置、护理计划与日历。
- 类别可拖动；项目只在所属类别内拖动，不可跨类别。关闭项目保留排序，再次开启恢复原位。
- 类别顺序、项目顺序、启用状态和快捷槽位均为设备本地设置。

### 照片与本地事务

- 所有 Record 类型与 CarePlan 共用备注附件概念，不再把新照片只嵌在 Memo/Diary payload。
- 每个实体最多三张照片；Diary 同样执行三张限制。现有一至三张历史 payload 照片兼容读取并可在后续编辑时规范到公共附件。
- 编辑器提供缩略图、单张大图、最多三张左右滑动和删除/替换入口。照片导入失败不得破坏已有草稿。
- Record/CarePlan 的本地保存与照片关联变更在同一数据库事务提交；软删除同时产生媒体 tombstone。
- 转 Record 为 CarePlan 时附件所有权在同一事务转移或重建；任何失败都保留原 Record 完整可见。

### 原子家庭同步包

- 记录同步包由 Record 元数据、全部有效照片引用与照片字节构成；计划同步包由 CarePlan 元数据、全部有效照片引用与照片字节构成。
- 发送端先上传所有照片到 NAS 暂存区，全部确认后才原子发布实体和完整引用；发布失败不得留下可查询的部分包。
- 接收端先下载元数据与全部照片到本机暂存区并校验，全部成功后在单次应用事务使新版本可见。
- 新包失败时接收方完全不可见；编辑包失败时继续显示旧完整版本。不得用占位图暴露部分状态。
- CarePlan 包未完整应用前不得建立本机提醒或系统日历副本。
- 创建者本机保存不等待 NAS。未发布时显示琥珀状态，详情说明其他成员暂不可见；计划还需说明其他成员暂不会提醒。
- 用户可手动重试；后续前台同步和手动拉取也重试。创建者本机提醒与系统日历基于完整本地事务，可独立工作。
- Record/Plan 与照片发布日志属于同一原子同步过程，不定义“有同步日志但无照片上传”的独立成功状态。

### 系统日历与提醒所有权

- 乐记是 CarePlan 唯一权威来源；Android 系统日历只是当前设备的单向投影。系统日历中的编辑或删除不反向修改计划。
- 每条计划“同步到系统日历”默认开启，但当前设备完成权限、目标日历与披露配置后才真正创建副本。
- 首次主动启用时按需申请权限、列出可写日历并要求明确选择。不得静默采用默认日历；被动同步收到计划不得触发授权。
- 权限拒绝、取消、写入失败或目标日历消失均不阻断本地保存和家庭同步，只产生可恢复提示。
- 本机维护计划 UUID 与 event ID 映射；删除、跳过、履行或编辑计划时只处理乐记拥有的副本。
- 三级披露固定为：
  1. 标题仅“乐记 · 护理计划”；
  2. 标题“宝宝昵称 · 记录类型”（首次配置默认）；
  3. 标题同第二级，描述可含文字备注；有照片时写“照片 N 张，打开乐记查看”及应用深链。
- 任何级别都不得把照片字节或可由日历账户直接获取的照片 URI 交给系统日历。
- 更改披露只重投影尚未发生的计划，不批量更新历史事项。
- 每台设备为每个计划选择一个提醒所有者：系统日历副本成功时由其在开始时提醒并取消乐记重复通知；否则由乐记安排非精确提醒。
- 家庭计划本机提醒默认开启、可本机关闭且不同步。其他成员履行后在下一次前台同步取消；离线设备允许一次陈旧提醒。

### 不可保存确认态

- 业务校验失败时主确认按钮保留正常形状、尺寸和排版，使用浅灰填充、灰色描边、无阴影。
- 该状态“可请求解释但不可保存”：点击不持久化，在按钮正上方显示非模态原因卡，并定位、聚焦和高亮第一个无效字段。
- 原因卡只显示具体问题；不显示也不让辅助功能朗读固定“暂不可保存，点击查看原因”。
- 原因卡保持到字段修改、再次点击灰按钮或 Composer 关闭。字段修改后重校验，全部合法时立即恢复正常确认态。
- 保存中、删除中等忙碌态真正不可点击，也不打开原因卡。

### 模块与接口

- **主要领域 seam：CareLog。** 深化既有高层领域接口，使计划生命周期、Record↔CarePlan 转换、权限、履行裁决、本地附件事务与提醒决策都从同一入口发生。界面不得直接组合 DAO、outbox 或系统日历调用。
- **主要 UI seam：RecordComposer。** 扩展既有请求、草稿与状态，表达五类请求、三种可见模式、照片草稿、日历选择、校验原因和提交结果。测试断言状态/事件，不把内部 Composable 当契约。
- **家庭同步 seam：SyncPort。** 继续作为 NAS 所有权边界，承载计划、自定义定义、原子媒体包、权限拒绝与冲突收敛；领域层不感知 HTTP、暂存协议和游标细节。
- **系统日历 adapter：SystemCalendarPort。** 新增窄接口表达权限前置检查、可写日历枚举、事件 upsert/delete 和投影结果。Android provider 属于外部适配器，产品行为仍通过 CareLog 或内部协调器测试。
- 保持两个主要测试表面，不为计划状态、照片、权限、排序或提醒分别创建可被 UI 绕过的浅服务层。

## Testing Decisions

### 什么叫好测试

- 断言用户可观察行为和稳定领域结果：可见状态、权威记录、计划状态、附件集合、提醒所有者、权限结果、同步可见性和具体错误原因。
- 通过公开领域/Composer seam 建立输入并观察输出，不直接拼 DAO 行证明业务规则，也不依赖 private Composable。
- 时间测试使用可控时钟与显式 ZoneId；角色/冲突测试使用稳定 membership、确认时间和 UUID，不依赖真实墙钟或集合偶然顺序。
- 原子同步测试必须证明失败中间态不可见，而不只是成功路径最终有照片。
- 迁移测试从已发布 schema 构造旧数据，验证旧记录、旧照片、CalendarEvent 和快捷槽位兼容。

### 主 seam 1：CareLog

通过 CareLog 公开操作覆盖至少：

1. 当前/过去形成 Record；未来形成 CarePlan，且未来计划不进入记录查询、汇总、搜索或普通导出  
2. pending 随时钟派生 missed；到点或 skip 不生成 Record  
3. 履行在单事务创建关联 Record 并完成计划，失败不部分提交  
4. Record 改未来显式转换；tombstone、计划与附件一致，失败保留原记录  
5. CarePlan 改到过去仍是 missed 计划  
6. 任意成员履行与普通成员/管理员修改权限矩阵  
7. 创建者离开后的管理员接管  
8. 履行冲突按管理员、较早确认时间、UUID 裁决，且与到达顺序和实际发生时间无关  
9. 落选履行不进入普通记录表面；管理员转换后才出现独立 Record  
10. 今天分组/排序与非今天日期范围语义  
11. instant/创建时区跨时区显示和提醒稳定性  
12. 状态型项目安排不提前改变开放睡眠或计时状态  
13. Record/CarePlan 附件最多三张、软删除 tombstone 与本地事务原子性  
14. 系统日历失败不回滚计划；成功/失败选择唯一提醒来源  
15. 被动同步不申请权限；本机已配置才建立副本  
16. 历史 CalendarEvent 保持旧行为，显式转换才生成计划  
17. 自定义项目权限、定义快照与本机隐藏边界  

Prior art：既有 CareLog 测试已通过高层接口覆盖记录软删除不进汇总、睡眠状态事务、CalendarEvent 领域边界、自定义项目快照和同步触发。本功能延伸该风格，不另起只测 DAO 的平行套件。

### 主 seam 2：RecordComposer

通过 Composer 请求、草稿、状态与动作覆盖至少：

1. 五类请求恢复到正确草稿并呈现三种模式  
2. 新建时间跨越 now 后切换事实/计划，编辑记录跨未来出现转换确认  
3. 履行默认字段和照片带入，确认前可调整且最多三张  
4. 所有具体类型公共备注区提供相同照片能力；导入失败不污染当前草稿  
5. 非法草稿按钮状态、点击后具体原因、首字段定位和修正后恢复  
6. TalkBack 只包含具体原因，不包含被否决的固定提示  
7. 保存中/删除中不响应解释点击且不重复提交  
8. 切换或关闭会话后旧照片导入、保存、删除回调不能污染新会话  
9. 日历开关默认开；未配置进入授权流程，取消后计划仍可保存  
10. 母乳/睡眠计划在安排模式不启动状态动作，履行模式才显示相应选择  

Prior art：既有 Composer SavedState 与 SessionGate 测试已覆盖请求匹配恢复、照片异步隔离与旧会话回调拒绝，应直接扩展这些行为。

### SyncPort 集成与 NAS 契约

- 用现有真实同步端口夹具覆盖 CustomItemDef、CarePlan、履行候选和媒体包出站/入站；不把它提升为第三个 UI seam。
- 发送测试注入照片上传中断、最终发布失败、重试、编辑旧版本保留和 tombstone，证明 commit 前远端看不到实体。
- 接收测试注入第 N 张下载失败、校验失败、应用事务失败和重试，证明 Record/Plan、照片、提醒和游标只在完整应用后前进。
- 服务端契约覆盖包内引用完整性、暂存清理、幂等 commit、权限、分页/游标和并发履行裁决；原子拒绝不得接受部分实体或媒体。
- 至少一个双设备端到端：A 离线建带照片计划，B 不可见；A 完整发布后 B 一次性看见并提醒；双方离线履行后同步为唯一事实。

### SystemCalendarPort 契约与设备 smoke

- Fake adapter 用于 CareLog：权限拒绝、目标丢失、upsert 成功/失败、删除失败、三级披露和提醒所有权。
- Android adapter 契约验证只枚举可写日历、使用用户选择的 ID、写开始时提醒、保存稳定计划深链，且不写照片字节或可外泄照片 URI。
- 设备 smoke 覆盖真实授权/拒绝、目标选择、创建/编辑/完成/删除副本与深链返回。厂商差异不把投影失败变成计划保存失败。

### 设置、迁移与 UI smoke

- 设置测试覆盖四槽默认迁移、空槽、旧泛化引用清空、禁用后顺序保留、类别排序、项目不可跨类别与本机偏好不进同步 payload。
- 数据库迁移覆盖 CarePlan/履行/附件/定义字段和 tombstone，并证明旧 Record、旧一至三张照片、CalendarEvent 和自定义项目仍可读。
- Compose 只保留少量 smoke：四槽加更多与偏好手布局、待履行分组颜色、三级披露、照片预览滑动、灰态按钮原因卡。像素由截图/人工验收补充，不把内部层级当契约。

## Out of Scope

- 每日、每周、间隔或其他重复护理计划，以及重复实例批量编辑  
- 到点自动记录、自动履行或自动启动状态型记录  
- 系统日历双向同步、读取外部修改或导入普通日程  
- 把照片上传到系统日历账户或提供公开照片 URL  
- 后台常驻同步、轮询、FCM、P2P、家庭推送或为消除一次陈旧提醒新增实时通道  
- 精确闹钟权限；乐记回退继续使用非精确提醒  
- 云服务器或公网同步；继续遵守 NAS 中心、家庭 Wi-Fi 硬约束和前台同步  
- 新建自由标题 CalendarEvent，或自动/批量转换历史 CalendarEvent  
- 破坏性迁移或删除历史 memo、other、custom Record  
- 新建泛化“备注”“其他”“自定义”项目  
- 项目跨产品类别拖动或把本机项目布局同步给家庭成员  
- 四至九张历史照片的特殊产品迁移场景；用户已确认不存在该场景  
- 在普通时间轴、汇总、搜索或普通导出展示冲突未采纳履行  
- 账号体系、跨设备同一人身份合并或改变现有 membership 角色模型  

## Further Notes

- 本规格建立在“护理记录是事实、护理计划是意图”的术语边界上；实现与文案使用 `CONTEXT.md` 的统一词汇。
- 已接受决策包括：未来计划与记录分离、停止新建泛化记录入口、照片作为通用附件、系统日历三级披露、记录/计划照片原子同步、共享自定义定义但不共享布局。
- 当前代码已有 CareLog、RecordComposer、SyncPort、历史 CalendarEvent、媒体和本地提醒基础；本规格是已批准但尚未完成的扩展，不应把 PRD 设计文字当作已实现事实。
- 用户已确认测试边界：CareLog 与 RecordComposer 是两个主要产品 seam；SyncPort 做 NAS 集成/契约；SystemCalendarPort 仅作为 Android provider adapter，并通过领域行为验证。
- 实现可拆成纵向票单，但所有票单必须维护同一领域模型和原子包契约；不能长期发布“计划无照片”或“记录无照片”的元数据阶段。
- 发布位置：本地 issue tracker `.scratch/care-plan-record-customization/spec.md`。
