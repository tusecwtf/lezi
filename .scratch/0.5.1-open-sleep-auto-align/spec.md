# 0.5.1 开放睡眠不进自动近邻

## Problem Statement

两台设备（或同一人连点两次）在近邻时间窗内各自确认「睡下」后，家庭服务器按
ADR-0023 把这两条 SleepStart 自动写成来源关系。落选那条变成 **来源角色** 的
**投影开放** 睡眠：时间轴主路径不画它，底栏/头像却仍把它当成「正在睡、点醒来」。
家长看见一条画出来的睡眠、底栏却是「醒来」；确认醒来时本机发现快捷目标已被来源
关系藏起来，弹出「其他：出了点小问题」，既醒不了也撤不掉。这不是同步冲突收件箱，
也不是 tombstone。

现场（家庭 OPPO、发布 0.5.0）：下午一条开睡被收成来源后，底栏卡在「醒来」，时间轴
只有早晨那条已醒区间。调试本机覆盖安装对齐后的同号 0.5.0 后，底栏回到「睡眠」，
但存量来源开睡仍在库里。该本机包不是渠道 0.5.1。

## Solution

**0.5.1 同一维护窗同步升级 NAS 与两台 APK。不单发热修发版。**

- **以后新写的** 投影开放 SleepStart 不得进入自动近邻候选。等这条睡眠先有一条合法
  WakeObservation（或历史遗留 `end_timestamp`）再参与归组。已经闭合的近邻睡眠照旧
  自动收口。不自动闭合、不改绑醒来、不拆已写成的来源关系。
- **APK 对齐是 0.5.1 必带项**：底栏/头像只认可见开放睡眠；确认醒来看「这条是否仍
  投影开放」而不是「是否仍是可见快捷目标」；「睡眠状态已变化」走家里状态刚变了，
  不再显示成「出了点小问题」。醒来卡片上睡下、醒来两个时刻都可改（不再冻住睡下），
  确认后按卡片写回，防止再卡死。底栏/分类对齐工作树已有；两端可改是新增。
- 存量来源开睡（真机那条下午记录）**保持原关系**。新 NAS 不会修旧账；旧 APK 碰到
  这类存量仍可能卡，所以两台都要换成 0.5.1。

## User Stories

1. 作为同时开着两台设备的家长，我想在两台都点了「睡下」且主时间相差不超过三十分钟时，
   时间轴上仍能看见两条各自的开放睡眠，以便任一台都能点「醒来」结束自己看见的那条。
2. 作为刚点了「睡下」的家长，我不希望这条还没醒来的睡眠因为近邻同型被收成来源而从
   时间轴消失，以便我能从画出来的条子点进去或用底栏醒来。
3. 作为记录页上的家长，我只希望在有一条**可见**开放睡眠时看到「醒来」和「睡觉中」，
   以便底栏与时间轴说的是同一件事。
4. 作为只有一条来源角色开放睡眠、没有可见开放睡眠的家长，我想看到底栏是「睡眠」、
   头像不是「睡觉中」，以便我能再记一条新的睡下，而不是对着一条看不见的睡眠点醒来。
5. 作为确认醒来的家长，我想在这条睡眠仍投影开放时写出 WakeObservation，即使它已经
   是来源角色，以便存量卡死也能被本机醒来路径收掉。
6. 作为确认醒来时本机开放睡眠已经变了的家长，我想看到「家里的状态刚变了」而不是
   「其他：出了点小问题」，以便我知道该重新打开睡眠菜单，而不是以为程序坏了。
7. 作为这条睡眠的作者或 Owner，我想在「醒来」卡片上同时改睡下和醒来，以便记错区间
   时一次确认结束；家人没有改这条睡眠的权限时，睡下仍只读，他们仍能确认醒来。
8. 作为两条近邻睡眠都已经醒来的家长，我希望它们此时才自动写成来源关系，以便闭合后
   的近邻同型仍只计展示版、不双计时长。
9. 作为补记两条已经闭合、主时间近邻的历史小睡的家长，我希望它们在 commit 后立刻
   自动对齐，以便补记路径与喂养/换尿布一样收口。
10. 作为一条已醒、一条仍开放且主时间近邻的家长，我不希望开放那条被收进关系，以便
    正在睡的那条继续画在时间轴上、继续接「醒来」。
11. 作为记喂养/换尿布/用药的家长，我想让非睡眠近邻同型自动收口行为与 0.4.8/0.5.0
    完全一样，以便这次只改睡眠候选，不改其它类型。
12. 作为记用药的家长，我希望同名近邻仍按规范化名称分片、空名各成一组，以便睡眠规则
    不打穿名称分片。
13. 作为记自定义项目的家长，我希望仍按项目身份分片，以便睡眠规则不打穿自定义分片。
14. 作为写出 WakeObservation 的家长，我不希望醒来观察被收进来源关系，以便醒来仍是
    独立根、不是护理记录。
15. 作为家里已有一条开放睡眠的家长，我再开一条新睡下时，不希望服务器自动闭合或改写
    较旧那条，以便 ADR-0021 重叠开放睡眠仍然成立。
16. 作为已经给某条睡眠写了醒来的家长，我不希望自动收口把这条 WakeObservation 改绑到
    展示版睡眠上，以便观察仍挂在当初那条 SleepStart。
17. 作为已经有一条来源角色开放睡眠的家长（0.5.0 现场遗留），我不希望升级 NAS 后这条
    关系被拆掉或改写，以便服务器不回改已提交的 provenance。
18. 作为这台已经用本机包缓解过的家长，我想装上渠道 0.5.1，以便正式包与另一台、与
    更新目录是同一个 versionCode，而不是继续留着同号调试 0.5.0。
19. 作为第二台还停在渠道 0.5.0 的家人，我想在同一维护窗装上 0.5.1，以便旧客户端不再
    把存量来源开睡当成醒来快捷。
20. 作为家庭维护者，我不希望这次把同步最低 versionCode 抬到 31，以便偶尔漏升的旧包
    仍能同步；漏升的代价是旧死锁合同仍在，靠手升而不是强制更新壳。
21. 作为 NAS 操作者，我想在两台都装上 0.5.1 之后（或同一窗口内先 APK 后 NAS）再换
    容器，以便新收口与旧客户端对齐同时生效。
22. 作为离线时两台都写了近邻睡下、恢复后再同步的家长，我希望服务端 commit 后仍不把
    这两条开放睡眠收成来源，以便同步回来后两边都能醒来。
23. 作为同一账号在同一台机上连点两次睡下的家长，我希望两条开放睡眠都保持可见，以便
    误触连记也能分别醒来，而不是一条被藏起来。
24. 作为同一 membership 两台设备的家长，我希望「同作者也连边」只作用于**已经闭合**
    的近邻睡眠，以便开放阶段的双写不再触发来源角色。
25. 作为在同一 commit 里同时提交 SleepStart 与合法 WakeObservation 的补记路径，我希望
    这条睡眠按已闭合参与归组，以便一次写完的小睡仍能与近邻已闭合睡眠对齐。
26. 作为历史库里仍带遗留 `end_timestamp` 的已闭合睡眠，我希望它算作已闭合并继续参与
    近邻收口，以便迁移前的闭合睡眠不被新规则误判为开放。
27. 作为撤回了唯一合法醒来、使睡眠重新投影开放的家长，我不希望服务器因此拆掉已经
    写成的来源关系；若当时还没写成，则继续不收口，以便 D1 与 B1 同时成立。
28. 作为 Owner，我希望延迟收口之后仍可用改选展示版，以便自动对齐后的改选合同不变。
29. 作为看周汇总的家长，我希望两条近邻小睡都醒来并对齐之后只按展示版计一次时长，
    以便自动收口的汇总语义不变。
30. 作为看时间轴的家长，我希望来源角色记录仍只在展开来源时出现，以便主路径不画隐藏
    开睡、也不把它画成进行中条子。
31. 作为家庭维护者，我不希望这次新增 wire 字段、reason 枚举或 schema，以便 0.5.0
    客户端仍能拉关系；行为差只在「会不会把开放睡眠写进关系」。
32. 作为家庭维护者，我不希望把这次收口失败说成同步冲突或计划履行冲突，以便家长和
    后续工单都走来源关系，不走进收件箱。
33. 作为隔离实例上的维护者，我想在开发机 mktemp 数据根上证明「双开睡不收口、双闭睡
    仍收口、醒来后才收口」，以便证书测试永不打到家庭 NAS。
34. 作为 NAS 操作者，我想按既有 propose-then-confirm 换 0.5.1 容器，且普通 CD 不替换
    TLS 身份，以便这次只是版本替换不是证书事件。
35. 作为邀请安装新设备的家人，我想从目录装到 0.5.1 而不是旧的 0.5.0 目标，以便新机
    一加入就带对齐后的底栏与新收口。
36. 作为回滚 NAS 到 0.5.0 的操作者，我接受回滚后**新的**双开睡又可能被收口，但已按
    D1 写下的关系不会被这次回滚自动拆掉，以便回滚不改写 provenance。
37. 作为维护者，我想让失败分类继续复用「家里的状态刚变了」，不新增 FailureKind，以便
    文案目录不膨胀。

## Implementation Decisions

- **范围**：合同修订 + 服务端「开放等闭合再收口」+ 客户端对齐与醒来卡两端可改 +
  0.5.1 定名与同步升级。不单发热修 APK。不抬同步最低 versionCode（保持 21）。不拆
  存量来源关系。不自动闭合、不改绑 WakeObservation、不 tombstone、不合并字段。
  醒来卡不因此增加删除整条睡眠。
- **「投影开放」**：与 ADR-0021 投影同一条：该 SleepStart 没有合法 WakeObservation
  （未撤回，且 `wake_timestamp >=` 该睡眠 `timestamp`），也没有历史遗留闭合
  `end_timestamp`。不看 wire 上是否仍带 `end_timestamp` 键（新睡眠禁止该键）。有效
  观察指针未设时，最早合法未撤回观察仍使睡眠投影闭合。
- **B1 候选规则**：自动近邻在建连通分量之前，把投影开放的 SleepStart 从候选里拿掉，
  **再**对其余记录连边。种子自己是投影开放睡眠则本轮不对齐。剔除后仍 ≥2 条的闭合
  近邻（含非睡眠类型）按 ADR-0023 原规则收口。喂养/排泄子类不互并、用药名称分片、
  自定义项目分片、展示版排序一字不动。
- **闭合后补收口**：自动收口今天只在护理记录 commit 成功后、以已提交的记录 UUID 为
  种子。WakeObservation 不是 Record。因此：当一次 WakeObservation（或把睡眠第一次
  投影闭合的睡眠 mutation）被接受后，必须用**那条 SleepStart 的记录 UUID** 再跑同一
  套自动收口。只醒一条、近邻另一条仍开放时分量不足 2，不写关系；两条都闭合且仍落在
  近邻窗内，才写关系。同一 commit 里同时带上 SleepStart 与合法醒来的，按已闭合处理。
- **D1 存量**：不扫描、不解散、不改写已存在的来源关系。升级后的新规则只作用于之后
  的自动收口尝试。真机遗留的来源角色开放睡眠保持来源角色；新 APK 不再把它当作底栏
  快捷，旧 APK 仍会。
- **客户端对齐（0.5.1 合同）**：醒来快捷 / `hasOpenSleep` / 头像「睡觉中」只认非来源
  角色的投影开放 SleepStart。确认醒来的目标集合是「仍投影开放的 SleepStart」（含来源
  角色），不是「仍是可见快捷的那条」。时间轴主路径继续过滤来源角色 UUID。含「睡眠
  状态已变化」的失败归入家里状态刚变了，不新增 FailureKind。底栏/分类工作树已有，
  不得回退。
- **醒来卡两端可改（02，仅有权者）**：醒来时刻人人可改。睡下时刻仅当能管理该
  SleepStart 时可改（作者含同 membership 其它设备，或 Owner；与时间轴编辑同一 ACL）。
  有权且睡下有改动时，确认先写睡眠主时间再写 WakeObservation；无权或未改睡下则不发
  睡眠 mutation，确认只写醒来。不得因无权改睡下让醒来整单失败。醒来须晚于（改后的）
  睡下。不开放醒来卡删除整条睡眠。改睡下会移动近邻窗，闭合后按新主时间收口。
- **合同文档**：修订 ADR-0023 §4（睡眠）：写明投影开放不进自动候选、闭合后才收口、
  不拆存量。CONTEXT「疑似重复输入」与 data-model §5.2 补同一句。ADR-0021「不得自动
  闭合另一条开放 SleepStart」仍成立；本次是收口候选的收窄，不是改写睡眠区间。
- **Wire / schema**：零新字段、零新 reason、零 schema。`auto-near-neighbor:` 前缀与
  `auto_aligned` 加性字段保持。客户端仍不把该前缀写入本地 pull_summary mutation_id。
- **版本**：渠道目标 0.5.1 / versionCode 31；0.5.0 / 30 移入已发布源。Room 与
  local-data contract 不移动。服务端 Cargo 版本同号 0.5.1。更新目录最低仍 21。
- **发布顺序**：同一维护窗；推荐两台先装 0.5.1 APK，再换 NAS。先 NAS 后旧 APK 对
  **新**双开睡安全，但旧 APK 碰上存量来源开睡仍可能卡。不执行本 spec 里的 NAS CD；
  到发布票再 propose-then-confirm。VPS 路径保持放弃。
- **测试缝（现有最高缝，不新建门面）**：
  1. 护理日志门面的观察开放睡眠 / 确认睡眠（含改睡下时刻后确认醒来）。
  2. 家庭权威图在因果 commit 成功后的自动收口；醒来补收口种子是 SleepStart 的记录 UUID。
  3. 睡眠草稿/醒来卡片：两端时刻可点，确认后与写回一致。

## Testing Decisions

- 只测对外行为：有没有写成来源关系、底栏/头像认不认开放睡眠、确认醒来写不写
  WakeObservation、失败文案走哪一类。不测候选过滤的内部函数名，不新增第三套门面。
- **服务端（复用自动收口 store 夹具）**：两条近邻开放 SleepStart commit 后零来源关系；
  先后写出两条合法醒来后出现一条来源关系；两条已闭合近邻小睡仍立即收口；一条开放 +
  一条闭合近邻不把开放那条收进去；近邻喂养仍收口；WakeObservation 自己不进组；同一
  commit 带睡下+醒来的按闭合处理；历史遗留 end 算闭合。证书/替换证书测试只打隔离
  实例。
- **客户端（复用护理日志醒来测试族 + 失败文案测试 + 睡眠草稿/卡片）**：来源角色开放
  睡眠不是观察开放睡眠的快捷；用原 id 确认醒来仍写出观察；「睡眠状态已变化」归家里
  状态刚变了。醒来卡片两端可改，确认后主时间与观察与卡片一致。底栏/分类已有测试不得
  回退。
- **不单开**：同步冲突收件箱、计划履行、tombstone 复活。那些不是本缺陷。
- **发布冒烟**：Rust 三件套 + 相关 JVM；隔离实例双开睡/双闭睡；NAS 仅在 owner 确认
  CD 后按既有回滚手册做健康与证书指纹比对，再两台装 0.5.1 走一次睡下/醒来。

## Out of Scope

- 单独再发一版只含客户端的热修 APK。
- 自动解散或改写已存在的来源关系（含真机遗留那条）。
- 自动闭合另一条 SleepStart，或把 WakeObservation 改绑到展示版。
- 把同步最低 versionCode 从 21 抬到 31。
- 新 FailureKind、新 wire、新 schema、新 reason。
- 同步冲突收件箱、计划履行冲突、tombstone、字段合并。
- 在家庭 NAS 上做证书生成/替换/过期/错配测试。
- VPS 部署。本 spec 不执行 NAS `push-and-deploy`。

## Further Notes

- 现场机制：双 SleepStart → 自动来源关系 → 来源角色开睡被时间轴过滤、仍被旧 APK 当
  醒来快捷 → 确认醒来走「仍可见才算开放」→ 状态变化被分类成意外错误。不是冲突未采纳。
- 工作树已有客户端对齐与对应测试；服务端仍按主时间窗对开放睡眠连边。0.5.1 把两端收齐。
- 本机覆盖安装的同号 0.5.0 不是渠道目标；正式包是 31 / 0.5.1。
- 工单见 `issues/01`–`03`。01 与 02 无阻塞可并行；03 等 01 与 02。
