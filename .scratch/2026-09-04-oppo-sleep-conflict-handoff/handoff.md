# 判断：OPPO 0.4.5→0.4.7 后「昨天 ~21:42 睡眠」本机/远端对不上

日期：2026-09-04 · 联调机：妈妈 成员手机（成员手机，无线 ADB `192.168.50.x`）  
家庭：某家庭 · NAS `https://192.168.50.4:8765`（health `0.4.7` / schema 13 / ready）  
处置：用户已**手工**对齐本机与远端；本文只下判断，不改代码、不重部署。

## 先答两个问题

**不是「升级本身造了两条睡」。** 当晚是两段事叠在一起：

1. **整轮卡死（「待同步 12 项」）= 纯 0.4.5 客户端病。** 全量拉第二页把跨页重发实体 / 引用未就绪当致命错误，cursor 冻住，本机还能记、发不出去。升到 0.4.7 后这条主诉消失。见 `.scratch/0.4.5-sync-stuck-remediation/plan.md` RC1/RC2。
2. **残留「21:41 睡 · 家里没收下」= 卡死期间两边各自写的后果。** 0.4.7 第一次把卡死设备拉通，本机积压的那条睡撞上家里已经有的 ~21:42 睡。升级是揭示器，不是制造器。

**当前 tree / 现装 0.4.7（versionCode 28）不再埋「整轮卡死」那颗雷。** 跨页重发按幂等处理，引用未就绪有界跳过，全量重对账扛得住。0.4.7 **不会**再因为 NAS 重启换 generation、重登、或家庭实体超过一页就把自己卡死，然后在本机默默再记一条开睡。

0.4.7 里还在、但**不是这颗雷**的，是合同行为：

| 还在吗 | 是什么 | 算不算今晚那颗雷 |
|---|---|---|
| 不在 | 0.4.5「全量第二页必死 → cursor 冻 → 待同步 N 项发不出」 | **就是今晚的雷，已拆** |
| 在（合同） | 两台健康设备同一晚各记一条靠近的 SleepStart → 时间轴两条睡 +「疑似重复 · 待确认」（ADR-0021） | 不是。不需要 0.4.5 卡死，也不投影「家里没收下」 |
| 在（合同） | 同一 `client_uuid` 内容漂了 → `content_drift` / `branched`；状态行「家里没收下」或冲突收件箱 | 不是 bug。0.4.5 卡死期间本机改过已发表 UUID 时才会踩 |
| 在（运维） | NAS `generation` 仍是进程内 `secure_generation()`，容器重启强迫全家全量拉（`tools/lezi-sync/README.md`） | 对 **0.4.7 只是多拉一轮，扛得住**；对家里若还留着 0.4.5 设备，那台仍会死 |

爸爸机、其它未升的 0.4.5 设备：**那颗卡死雷还在它们身上**，与 OPPO 现装 0.4.7 无关。

## 当晚因果（升级前后都是实读）

| 时刻 | APK | 用户可见 |
|---|---|---|
| 升级前 | `com.lezi.babylog` **0.4.5 / versionCode 26**（`lastUpdateTime=2026-08-23`） | 「暂时无法同步 · 待同步 12 项 · 下拉重试」；点重试弹出 0.4.5 兜底「填写的内容不对 / 称呼空了，或邀请已经不能用」（分类器把未识别异常收成 `InvalidInput`，**不是**真的称呼/邀请坏了） |
| 23:29 | `adb install -r` NAS 渠道 APK | sha256 `0e603989…`、signer `ce1438c8…`（合同一致）、**0.4.7 / code 28**，数据保留 |
| 升级后主路径 | 0.4.7 | 12 项整轮卡死消失；家庭/时间轴可读；到 NAS `:8765` ESTABLISHED |
| 升级后残留 | 0.4.7 | 状态行「**护理记录 56cf2a7c · 家里没收下**」；明细「**21:41 睡眠 · 时长 9h59m · 仅本机 · 家里没收下**」（用户记成 21:42，差 1 分钟） |
| 用户手工处理后 | 0.4.7 | 同一条变为「时长 9h19m · 暂定」；醒来观察「本人 · 07:40 · 有效观察」可打开。用户确认根因是**本机与远端各有一条昨天约 21:42 的睡眠，对不上** |

`家里没收下` 在 0.4.7 不是「同步又卡死」，而是终态拒绝回执（`UnacceptedFactPresentation`）：某次因果 commit 被服务端 `status=rejected` 且 `code` 落在 `CausalSettlement.isTerminalRejectionCode`（含 `content_drift`、`incomplete_group`、`invalid_domain`、`already_related` 等）。时间轴「仅本机 · 家里没收下」只对**本机仍 dirty / 有未接受回执**的行显示。

NAS 库与 `mutation_receipts.code` 当晚读不到（SSH 用户无免密 sudo）。精确拒绝码以用户手工处理时看到的冲突面 / 回执为准，本文不把「同 UUID 漂移」和「两 UUID 近邻」钉死成同一种。

## 为什么升级后整机像好了、只剩这一条

0.4.7 把「拉失败就整轮死、12 条全发不出」改成：能拉的拉完，能发表的发表，**一条终态拒绝单独占状态行**（具名短 id）。所以：

- 主诉「无法同步」= 0.4.5 RC1/RC2，装 0.4.7 解除。现码只把**同一页**重复实体当错，跨页重发按合同幂等（`ReplicaSyncEngine`）；引用未就绪记台账、有界跳过，不冻 cursor。
- 残留 `56cf2a7c` = 卡死窗口里本机写下的那条睡，拉通后对不上家里已有的 ~21:42 睡。
- 手工对齐（撤回本机条 / 选家里的为展示或有效观察 / 在冲突面选一边）后，本机条不再 dirty，状态行应回「已同步」。

0.4.7 **自己不会无中生有造出 21:42 双睡**；它只是第一次让卡死设备看见远端、并试图发表本机积压。

## 以后怎么认

时间轴「仅本机 · 家里没收下」+ 状态行「护理记录 &lt;8hex&gt; · 家里没收下」+ 一条昨晚开睡时长被撑到次日清晨；对端同一分钟另有一条睡。不要被 0.4.5 的「称呼/邀请」弹窗带偏。

若两台都已是 0.4.7、同步健康、仍出现两条靠近的开睡：那是 ADR-0021「疑似重复 · 待确认」，按确认/撤回处理，不要再记一条「正确的」睡去覆盖。新开睡不得自动改写较旧开放睡眠（`docs/prd/data-model.md` §3.5.1）。
