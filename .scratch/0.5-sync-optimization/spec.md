## Problem Statement

家庭两台设备今天各自要为「确认自己和服务端一致」付出全量代价:服务端在**每个 pull 页**
都全家庭扫描+排序+SHA-256 重算 live census(且在 family 锁内),客户端**每一轮**都对 7 张表
全量重算本地 census——校验成本 ∝ 家庭规模 × 轮频,数据越攒越多越慢。同时,安静时打开 app
的一轮同步要发 3 个网络请求(握手 + 必为空的 pull + 更新检查),轮末还主动拆光连接让下一轮
重付 TCP+TLS;历史缺的照片按张串行下载。心跳 30s 的探针频率在安静期也偏频。
以上全部对用户不可见地消耗时延、电量和 NAS 的锁时间——「同步快不快」今天由这些隐形成本决定。

## Solution

零 wire、零 schema、响应逐字节不变的四个优化 + 一次心跳放宽(全部纯内部,老客户端/老服务端
任意组合行为不变):

1. **校验免每轮全量**:服务端 census 改为按 (family, head) 的进程内缓存——同一个 head 下
   第一次重算、之后 O(1) 命中,缓存失效只有两条规则(全部 rev 自增的唯一通道单点失效 +
   灾难恢复类绝对 rev 写入无条件失效),不做写路径增量折叠(结构上不存在「半折叠却当新鲜」
   的错误状态)。客户端安静轮(本轮零应用、零本地写、零待发布)直接复用上次 census,
   否则单次本地重算;任何全量重走结束时强制丢弃缓存重算一次,保证比对值永远可追溯到真值。
2. **安静轮零数据 RTT**:前台返回轮若最近一次心跳已证明「服务端无新数据且目录未变」,
   且无灾难恢复/清理/待发表/缺图挂起,则整段跳过握手+空 pull(新鲜度窗 = 心跳退避顶 300s,
   锚点是上次成功整轮)。轮末 keep-alive 从「全拆」改为 90s 空闲 TTL(身份驱逐语义原样保留);
   更新检查只在用户真实触发或距上次成功检查 >1h 的既有轮上 piggyback(不新增任何唤醒源)。
3. **照片补图 2 并发**:历史缺图路径改为 Semaphore(2) 并行下载,预算/上限/失败整页弃语义不变。
4. **心跳放宽**:基线 30s→60s、退避顶 120s→300s(降级梯 30s/120s/600s 一字不动);
   「对端写入可见性上限」验收显式改写为「心跳间隔 + 一轮」。

用户唯一可感变化:更新横幅出现可能晚至 1 小时,以及两台设备互见时延上限从 ~30s 放宽到
~60s(+一轮)——两者都是 owner 拍板接受的交换。

## User Stories

1. 作为两台设备同时开着的家庭成员,我想在对端记录喂养/换尿布后,最迟约 60s(一个心跳周期)
   加一轮同步内本机时间轴自动出现该记录,以便维持「不用手动刷新」的体验(此为 0.4.8 验收
   第 1 条的 60s 版显式改写,不是退化)。
2. 作为打开 app 但没有任何变化的用户,我想让前台返回轮不再发「握手+空 pull+更新检查」
   三个请求(心跳已经证明无新数据时整段跳过),以便打开即用、零等待零流量。
3. 作为家庭数据已积累数百行并继续增长的用户,我想让「确认与服务端一致」的校验成本只随
   变更量付费(每变更 head 一次、安静轮零次),而不是每轮全量重算,以便数据增长不拖慢同步。
4. 作为 NAS 维护者,我想让服务端 census 重算从每页一次降为每 head 至多一次、重启后每家庭
   只惰性重建一次,以便 family 锁持有时间和 CPU 不随页数/轮频放大。
5. 作为照片记录多的家庭成员,我想让历史缺图补下载两张并行,以便照片轮墙钟近线性缩短,
   且任一张失败时整页作废、绝不出现半包可见。
6. 作为夜间被动使用的用户,我想让心跳无变化时退避到 300s(±20% 抖动),以便无线电回低功耗、
   探针数比 0.4.8 减半以上。
7. 作为家庭的服务端从 0.5 回滚到 0.4.8 的用户,我想让客户端行为完全退回现状(零 wire 改动,
   响应逐字节不变),以便回滚零风险。
8. 作为灾难恢复后(服务端水位回退、待重对账、本地清理未完成)的用户,我想让上述「跳过」
   优化被一票否决、恢复轮照常完整执行,以便省电优化永不推迟修复动作。
9. 作为有历史缺图的用户,我想让「已确认 404 的缺图」不阻止 tip-skip、也永远不停止补图重试,
   以便优化不被一条死图永久钝化、图回来了能自动补上。
10. 作为设备/成员被移除后重加的用户,我想让 pending local-clear 与 reset 回执未消费时
    照常开整轮,以便删除恢复语义不被跳轮破坏。
11. 作为等待应用强制更新的用户,我想让更新横幅最迟在「真实触发」或「1 小时定时」内出现,
    且强制更新壳的降级/拆壳判据(AUDIT-20260801-P1-01)只应用在仍做 piggyback 的轮上,
    以便节流不破坏强更安全。
12. 作为乐记维护者,我想让全部改动零 wire、零 schema、golden envelope 逐字节不变,
    以便 0.4.8 客户端对 0.5 服务端零感知、revert 即回滚。
13. 作为乐记维护者,我想让服务端缓存失效只有「rev 自增单点 + 绝对 rev 无条件失效」两条
    规则,以便未来新增写路径不可能造出陈旧却自称新鲜的 census(漏一条=多一次重建,永不错值)。
14. 作为乐记维护者,我想让客户端任何全量重走结束时强制重建本地 census 缓存,以便缓存漂移
    的最坏结局是「恰一次额外重走」而不是永久假诊断。
15. 作为乐记维护者,我想让 tip-skip 跳过握手期间服务端版本 floor 仍由心跳端点强制,
    以便跳轮窗口内不存在「旧客户端连上新服务器」的无网期。
16. 作为 NAS 操作者,我想让 0.5 发布前置(打包 stanza + 配对断言 + docker 权限窗口)显式
    列在发布门里,以便按 propose-then-confirm 流程一次走通,而不是在 CD 脚本里撞 exit 1。

## Implementation Decisions

- **范围(Tier 1)**:W0 度量 → W1 服务端缓存 → W2 客户端复用 → W3 安静轮瘦身 →
  W4 媒体并行 → W5 心跳放宽;W2-W5 可并行开发,W1 随任意服务端窗口先出。
  XOR 多重集摘要 wire 增量(census_xor_v1)**挂起**,复活触发条件与全套失败安全条款
  见 design.md §1.3 + 附录 A,触发前不开发。
- **W1 服务端 census 缓存**:AppState 内短临界区互斥的 per-family 条目(epoch, head_rev,
  census);读在既有 family 锁内的 blocking 段,miss 惰性重建。失效规则仅两条:全部
  `rev=rev+1` 形态经手的唯一通道(advance_rev)推进即删条目;灾难恢复/导入/匿名化类的
  绝对 rev 赋值路径无条件删条目。缓存键含代际标识防「回退后 rev 复用」。只读连接不写缓存。
- **W1 读路径减负**:`close_empty_open_conflicts` 从 pull 读路径移到写事务(commit 派发
  末尾 / resolve / withdraw,拆接受事务参数的内部函数),保留「闭合推进 head 与实体 rev」
  的投递语义;存量与恢复残留的 empty-open 行由启动/周期维护兜底(媒体 GC 已有同款先例),
  防只-pull-不写的设备永远收不到冲突闭合。
- **W2 客户端 census 复用**:一轮 pull 全部页实体为空 ∧ deferred 未解决集空 ∧ cursor 未动
  ∧ 无待发布单元 ∧ 无待 generation 重对账 → 复用上次 (generation, census);否则单次全量
  重算(现状语义)。任何 cursor=0 重走结束时无条件丢弃缓存全量重算。不引入 Room
  InvalidationTracker(异步派发无 ack,兜底名不副实)。
- **W3 tip-skip**:谓词一票否决制 = 无待 generation 重对账 ∧ 无 pending local-clear ∧
  重置回执账本空 ∧ 无待发布单元 ∧ 无缺图(全部缺图为已确认 404 时放行;404 确认态耐久
  标记走既有 transport journal,无 schema 变更)∧ 心跳新鲜证明 ∧ 距上次成功整轮 ≤ 新鲜度窗。
  新鲜度窗 = 心跳退避顶(60/300 档即 300s),窗常量与心跳策略共享来源并有一致性测试;
  锚点 = 上次成功整轮完成时刻(心跳只做 head 未动的负向证明)。跳过轮不得弄脏熔断器/
  同步状态行/最近健康时间。跳过握手的安全论证:心跳端点仍过服务端版本 floor。
- **W3 keep-alive**:轮末全拆改 90s 空闲 TTL(< 平台连接池超时,不双花);origin+SPKI 身份
  变化立即驱逐的语义原样保留(TOFU 安全缝);冲突路径 5 处轮外拆除保持现状。
- **W3 更新检查节流**:门控 = 用户真实触发(回前台/下拉)∨(距上次成功检查 >1h ∧ 本轮因
  其它原因已发生);不新增任何唤醒源(仅前台红线);AUDIT-20260801-P1-01 判据只应用于
  仍 piggyback 的轮。
- **W4 媒体并行**:一期仅历史缺图路径(downloadMissingMedia)并行,Semaphore(2);尝试次数
  与字节上限改原子;404 按 media 独立 continue;任一 worker 非 404 失败 → 整页作废
  (零行写入、cursor 不动)。3×10MiB 堆峰值写进设计。staging 段并行是可选二期,原子接收
  合同(全部字节先落 staging 再进 Room)不变。
- **W5 心跳**:基线 60s、退避顶 300s、±20% 抖动、降级梯 30s/120s/600s 不动;文档同步点
  = wire 合同 §1.5 限流子弹的节奏数字 + 服务端限流注释的基线假设;验收改写为
  「对端写入可见性上限 = 心跳间隔 + 一轮」。
- **W0 度量**:隔离实例(现成 JVM harness:mktemp 数据根 + 直供证书,天然合规证书隔离)
  + store 级种子计时测试(1k/10k 行 census 重建中位数)+ census 开关端到端差值 +
  debug 日志每请求耗时 + 冷启动首拉/待发布检查/缺图查询/媒体串行并行墙钟;产出注明
  测量环境,写入 design.md §7 作为验收对照。
- **发布门**:0.5 版本定名时随发布工单补打包脚本的 0.5 stanza 与 validate 配对断言
  (server schema 仍 13、rollback source 0.4.8/13、APK code 顺延、floor 不动)——
  0.4.8 的同款缺口已在 2026-09-05 评审后的提交中解决,0.5 不提前猜版本号写死;
  P2-7(操作者 docker 权限窗口)由 owner 排期,解前 W1 不上 NAS、0.5 APK 不走 OTA。

## Testing Decisions

- 原则:只测外部可观察行为——响应字节、轮请求序列、可观察状态(状态行/熔断器/最近健康时间)
  ——不测内部缓存实现;golden envelope 逐字节比对是「对 0.4.8 客户端零影响」的直接证据。
- 服务端(Rust 三件套门禁 + store 级测试):对 store 全部公共写 API 逐个调用后断言缓存与
  全量重算黄金值一致(失效路径黄金测试);重启惰性重建一次;多 family 隔离;只读连接旁路;
  存量 empty-open 残留 + 只 pull 设备经启动维护闭合;census 开/关同请求逐字节相同。
- 客户端(JVM):零应用谓词矩阵(任一子句真→重算);pull 进行中本地写的竞态行为
  (假失配→恰一次重走→无风暴);复用条目在 generation 变化后失效;重走后强制重建;
  tip-skip 一票否决矩阵(五缝各一条)+ 心跳 kick 的 NeedsSync 轮不被吞 + 跳过轮状态不脏;
  keep-alive TTL 过期拆除/身份变化立即驱逐/心跳把手跨轮存活;更新检查节流行为
  (含 AUDIT-20260801-P1-01 回归组);故障代理下跳过轮 0 数据请求;媒体并发上限 ≤2、
  上限并发下仍被尊重、单 worker 失败整页弃、预算耗尽 checkpoint 留队;心跳常量更新断言
  + 降级梯不动断言 + 新鲜度窗=退避顶一致性断言。
- 先例与基建(直接复用,不新建 seam):服务端 store 测试族的 census 黄金值测试;
  客户端的 census 对账测试、keep-alive 测试、心跳循环测试、app-update 测试族、故障代理、
  隔离实例 harness、假后端/录制后端。
- 冒烟:Rust 门禁全绿后,隔离实例上按 AGENTS.md 流程验证(证书测试隔离规则适用);
  NAS 侧发布按 propose-then-confirm,发布门未解前不执行。
